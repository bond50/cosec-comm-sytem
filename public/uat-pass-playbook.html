COSEC Fresh-Start UAT Script

Manual test script for a fresh database: reset, rebuild the county structure, verify access, run the full correspondence cycle, and check documents, meetings, notifications, search, dashboard, and reports. Written so that anyone can pick this up cold — no prior knowledge of COSEC is assumed.

Target Workspace County Government of Vihiga
Central Office Office of the County Secretary and Head of Public Service
UAT Mode Clean manual database, no demo seed
Primary Purpose Validate workflow, access, movement, and accountability

How To Use This Guide

Four things to know before you start — read this once, then just follow the steps top to bottom.

1

Go in order

Steps build on each other — a later step often reuses an account, department, or record created earlier. Don't skip ahead on a first pass.

2

Copy, don't retype

Anything shown as a highlighted chip or in a dark code block is exact test data — click it to copy, then paste it straight into the matching field.

3

Check "Expected"

Every action is followed by an Expected list. If what you actually see doesn't match, that's a possible defect — write it down using the format in Section 14.

4

It's all fake data

Every name, office, and note in this guide is fictional test data for a fictional county. Reuse it freely, every time you run this script.

1. What This UAT Covers

This playbook covers the implemented app from first login to advanced workflow verification.

Foundation

Auth entry, organization setup, departments, members, roles, and access restrictions.

Business flow

Correspondence registration, review, routing, dispatch, acknowledgement, feedback, closure, reopen, and second cycle.

Supporting modules

Documents, meetings, action points, notifications, search, dashboard, and reports.

2. Before You Start

Check Expectation
Application starts pnpm dev runs without fatal startup error.
Database connection Prisma can reset and migrate successfully.
File storage Attachment upload is configured for local UAT.
Email delivery Optional for UAT. If email is unavailable, use already accessible accounts or local bypass flow.
Browser access http://localhost:3000 opens.
Use a clean browser profile or private window if previous sessions or organization state keep affecting results.

3. Reset And Start Fresh

Step 0: Reset Database

Run only this:

pnpm prisma migrate reset --force

Do not run:

  • pnpm run db:reset:uat
  • pnpm run db:seed:county

Expected: all data is removed, but all tables and migrations remain intact.

Also clear your browser's cookies for localhost:3000 (or use a fresh private/incognito window) right after this step, even if you don't feel logged in. Sessions use the JWT strategy, so a leftover session cookie from before the reset is not invalidated by wiping the database — NextAuth will keep treating you as signed in as a user that no longer exists until that cookie expires or you explicitly sign out. Skipping this is the single most common cause of confusing, contradictory behavior right after a reset.

Step 1: Start App

pnpm dev

Open http://localhost:3000 in the clean browser window.

Expected: auth entry page loads without crash and lets you proceed.

4. Auth And First Access UAT

Login and registration share a single email-first form at both /auth/login and /auth/register. Enter an email first; the form then shows a register step (new email) or a password step (known email).

Step 2: Create First Account

Open /auth/register. Enter your test email and press Continue.

Expected:

  • A Turnstile bot-check widget appears under the form. In a local NODE_ENV=development run it shows "Turnstile bypassed in development" and does not block submission.
  • Because the email does not exist yet, the form switches to a create-password step (password + confirm password).

Submit a password. Expected:

  • Account is created.
  • A message tells you to check your email to verify the account. If no real email service is configured for local UAT, the message instead shows a "Development verification link" directly on screen — this is expected, not a bug.

Step 3: Verify Email To Activate Account

Open the development verification link shown on screen (or the real email link if email delivery is configured). This opens /auth/activate?token=....

Expected:

  • Activation page shows a success state, not an error.
  • The account's emailVerified is now set. An expired or reused token should show a clear failure state instead of a crash.

Step 4: First Login

Return to /auth/login, enter the same email and the password you created, and submit.

Expected:

  • Login succeeds without a 2FA code prompt.
  • Because this account has no organization yet, the system redirects straight to /dashboard/organization/setup — no mandatory MFA challenge at this point, since the account holds no admin role until an organization exists.
Forgot-password flow (/auth/reset → /auth/new-password) is exercised later in Step 10, once a disposable test account exists, so this bootstrap account's credentials are not disturbed.

Step 5: Create Organization

Create this organization exactly:

Name County Government of Vihiga

Expected:

  • Organization is created successfully.
  • You become the first organization admin/member.
  • The setup flow also creates the central office automatically: Office of the County Secretary and Head of Public Service (OCS-HPS).
  • The same page (/dashboard/organization/setup) immediately switches to a department step — no page navigation, just the form changing in place — instead of sending you to the dashboard. The dashboard only opens once you finish or deliberately skip this step.

  • It is clearly shown as the central office.
  • Status is ACTIVE.
  • Description confirms it handles registration, review, dispatch, oversight, and closure.
  • The wizard's progress panel marks "Central office created" without you doing anything.

Step 7: Create Execution Departments

Use the "Create entity" form directly on the wizard page (the same form used everywhere else in the app). Create at least these departments:

Name Code Kind
Department of Health Services HLT Execution unit
Department of Transport and Infrastructure TRN Execution unit
Department of Finance and Economic Planning FIN Execution unit

Expected:

  • They are not marked as central office.

  • The wizard's progress panel updates after each one, listing the departments you've added so far.

Click through to the dashboard once done.

The dashboard itself stays deliberately minimal now — no setup checklist or "what's missing" nagging. To add more departments later (outside of first-time setup), open /dashboard/departments and use the "Setup wizard" link in its header, which reopens this same guided page.

6. Members And Role Assignment UAT

Step 8: Create Test Accounts

Create these role accounts through the "Create member account" dialog on /dashboard/members (click "Add member", or go straight to /dashboard/members?create=1). This sets a working password directly and marks the email pre-verified — no activation email needed for these accounts:

User Department Roles
Registry Officer Office of the County Secretary and Head of Public Service REGISTRY_OFFICER
Reviewing Officer / County Secretary Office of the County Secretary and Head of Public Service REVIEWING_OFFICER + MANAGEMENT
Health Officer Department of Health Services DEPARTMENT_USER
Transport Officer Department of Transport and Infrastructure DEPARTMENT_USER
Limited Guest User Office of the County Secretary and Head of Public Service USER
Double-check spelling as you type these names — a typo here (e.g. "County Secretar" instead of "County Secretary") will show up everywhere that account's name is displayed later: movement history, meeting organizer/chairperson, action point assignee. It is not a bug in the app if it happens, just a data-entry slip that is worth avoiding.

Expected:

  • Central-office roles only appear when the central office department is selected.
  • Execution departments show execution-appropriate roles such as DEPARTMENT_USER.
  • You should not be able to assign REGISTRY_OFFICER to Health, Transport, or Finance.
  • Department is mandatory for active members.
  • The bare USER role saves and produces a constrained member with minimal access (used later in Step 12).
SUPER_ADMIN is intentionally not selectable anywhere in this form — it is a reserved support/recovery role that can only be set directly in the database, not through normal onboarding. Treat it as out of scope for routine UAT unless the office specifically asks for a database-level test of it.
Admin-created passwords deliberately skip the strong-password rules (minimum 4 characters, e.g. 1234) since they're temporary and handed off by an administrator. Each of these accounts is forced onto a "Set your password" screen the first time they log in, before reaching the dashboard — expect this the first time you sign in as Registry Officer, Reviewing Officer, Health Officer, Transport Officer, or the Limited Guest User in the steps below. Once that first-login password change is done, normal sign-in resumes as usual.

Step 9: Verify Member Detail

Open each member detail page.

Expected:

  • Assigned roles display correctly.
  • Department is visible and correct.
  • Status is ACTIVE for the working accounts.
  • Multi-role membership is shown correctly where applicable.

Step 10: Password Reset Flow

Using the Health Officer test account, sign out and open /auth/reset. Submit its email.

Expected:

  • A generic confirmation message appears regardless of whether the email exists, so the flow does not leak which accounts exist.
  • In local UAT without email delivery, the message additionally shows a "Development reset link" on screen.

Open the reset link (/auth/new-password?token=...) and set a new password.

Expected:

  • New password is accepted and saved.
  • The old password no longer works.
  • Login succeeds with the new password.
  • An expired or already-used reset token shows a clear failure state instead of a crash.

7. Access Control UAT

Step 11: Mandatory MFA Challenge For Admin Roles

Sign out of the account you used to create the organization (it now holds ORG_ADMIN). Sign back in with its email and password.

Expected:

  • After password sign-in succeeds, you are redirected to /auth/2fa instead of straight to the dashboard, because ORG_ADMIN is an admin role.
  • Requesting a code sends one by email; in local UAT without email delivery it is shown on screen as a development verification code.
  • Entering the correct code completes sign-in and reaches the dashboard.
  • An incorrect or expired code is rejected with a clear message.

Then test enforcement directly: in the same authenticated browser, before completing the challenge, try navigating straight to /dashboard in a new tab.

Expected:

  • You should be sent back to the MFA challenge, not allowed into the dashboard. If the dashboard opens without completing the code step, log this as a defect — MFA is meant to gate access, not just redirect once after login.

Step 12: Wrong-Destination Blocking

Login as a DEPARTMENT_USER, for example Health Officer.

Try to open these routes directly:

  • /dashboard/members
  • /dashboard/access
  • /dashboard/correspondences/register

Expected:

  • The user cannot manage members or access policy.
  • The user cannot register correspondence.
  • The app redirects to dashboard or blocks the route without exposing unauthorized controls.

Then check allowed areas:

  • /dashboard
  • /dashboard/correspondences
  • /dashboard/documents
  • /dashboard/meetings

Expected:

  • Page opens only where the role has view permission.
  • The user sees limited business information, not management controls.

Step 13: Access Module Walkthrough

Login as Reviewing Officer / County Secretary (or Org Admin) and open /dashboard/access.

Expected across its three tabs:

  • Role guide — the current-role card shows the correct role, and clicking each role in the filter list on the left updates the summary, placement, and responsibilities shown.
  • Allowed pages — switching roles updates the allowed pages and actions lists and the permission table to match that role only.
  • Rules and mapping — the page/action mapping table updates for the selected role and matches what that role can actually reach in Step 12.

Then login as Health Officer (DEPARTMENT_USER) and confirm this page is blocked per Step 12, not just informationally hidden.

Step 14: Forbidden Page Check

While logged in as Health Officer, try to open a page reserved for a role this account does not hold, for example /dashboard/organization/setup or an admin-only action route.

Expected:

  • You land on a clear "not authorized" experience (redirect or the /forbidden page) — never a raw error, blank screen, or crash.
  • The forbidden page offers a way back into allowed areas of the app.

8. Correspondence UAT: Full Lifecycle

This is the most important test in the entire app.

Step 15: Register As Registry Officer

Open /dashboard/correspondences/register. This form is incoming-only for phase 1 — there is no "Type" field to fill in; every record registered here is automatically type Incoming. Any grey placeholder text you see in empty fields (e.g. "Deployment", "CO PSM&ICT", "Felix Otiato") is just an example hint pulled from historical sample data — not a required value.

The very first field after the received date is Source type — a two-button choice between Internal county office and External sender. Pick External sender for this run and use this test data:

Received date and time Now
Source type External sender
Subject Request for road repair status update
Description Requesting a status update on road repair works in Vihiga.
Sender name Jane Atieno
Sender office Office of the Governor
Delivered by John Courier
Registry receiver Leave as "Use current signed-in user" — this is who the record's "received by" is set to.
Delivery method Hand delivery
Priority Urgent
Confidentiality Internal

Expected:

  • The record saves without validation error.
  • Reference number is generated automatically.
  • Reference format is office-readable, for example VCG/OCS/2026/04/000001.
  • Status starts as NEW.
  • Received by is the Registry Officer.
  • There is a first audit entry and first movement entry.
  • On the detail page, the "Source" field reads Office of the Governor · External sender.
Later, try registering one more item and picking Internal county office instead — you then pick an executing department from a dropdown rather than typing a sender office by hand. The "Source" field on that record's detail page should instead read something like Department of Transport and Infrastructure (TRN) · Internal county office. This confirms the source is a real, structured link to a department, not just a free-text guess.

Step 16: Review As Reviewing Officer / County Secretary

Open the new correspondence detail page.

Save review instructions only:

Please verify road repair progress and return feedback with current status.

Expected:

  • Status becomes UNDER_REVIEW.
  • Reviewer identity is stored.
  • Instructions appear in the review block.
  • Audit and movement reflect the review action.

Use this routing decision:

Expected:

Use this dispatch note:

Expected:

  • Status becomes DISPATCHED.
  • Dispatch history shows central office to Transport destination.
  • Movement history reflects dispatch issuance.

Step 19: Confirm Receipt As Transport Officer

Login as Transport Officer and open the same correspondence.

Expected before action:

  • Transport Officer sees Confirm receipt.
  • Transport Officer does not see review, routing, or close controls.

Confirm receipt.

Expected after action:

  • Dispatch acknowledgement timestamp is stored.
  • Status becomes IN_PROGRESS.
  • Movement and audit show acknowledgement.

Step 20: Submit Feedback As Transport Officer

Use this feedback note:

Road repair progress verified. Works are ongoing and the department will submit the final completion report after site confirmation.

Expected:

  • Feedback timestamp is stored.
  • Status becomes AWAITING_FEEDBACK.
  • Feedback note appears on the detail page.
  • Audit and movement reflect feedback submission.

Step 21: Close As Reviewing Officer / County Secretary

Use this closure note:

Feedback reviewed and accepted. Correspondence closed after Transport Department response.

Expected:

  • Close controls are visible only after feedback exists.
  • Status becomes CLOSED.
  • Closure note is visible.
  • No more workflow-action controls appear except a clearly distinct, amber-toned "Reopen" button — it is deliberately styled differently from the normal action buttons so it isn't clicked by accident.
  • Dashboard counts update accordingly.

Step 22: Reopen And Re-Dispatch

Reopen with this justification:

Additional clarification requested after closure. Reopening for follow-up review and routing.

Expected:

  • Only closure-authority role sees reopen.
  • Status returns to UNDER_REVIEW.
  • Upload becomes available again for authorized roles.

Then route and dispatch again to Transport Officer.

Expected:

  • A second dispatch cycle is supported.
  • Previous history remains visible.
  • Movement and dispatch history show both cycles.

Step 23: Complete Second Cycle

As Transport Officer:

  • Confirm receipt again.
  • Submit second feedback note.

Use this note:

Follow-up clarification completed. Transport Department confirms the updated road repair status has been reviewed and returned.

Expected:

  • Second acknowledgement is stored.
  • Second feedback is stored.
  • Both dispatch records remain visible.

Step 24: Close Second Cycle

Use this closure note:

Second feedback reviewed and accepted. Correspondence closed after follow-up clarification.

Expected:

  • Second closure completes successfully.
  • Status is again CLOSED.
  • Movement and audit reflect the second closure.
  • Movement history entries all show a real, verified "From" and "To" (a department/officer, or the intake source) — never a placeholder like a duplicated self-reference. If any row shows the same actor as both "From" and "To" with no real handoff, log it as a defect.

13. Dashboard And Reports UAT

Step 44: Dashboard Semantic Check

Open /dashboard as Reviewing Officer or admin.

Expected:

  • Counts reflect real test data, not placeholders.
  • Urgent items section reflects urgent correspondence.
  • Pending dispatches reflect active workflow state.
  • Unread notification count is correct.
  • Pending action point information appears where implemented.
  • Recent records are clickable.
A metric tile reading "0" is not automatically a defect. Each tile only counts records currently in a specific live state — for example, "Pending dispatch" only counts correspondence actually mid-dispatch right now, and "Department performance" only counts correspondence currently assigned to a department that hasn't been closed or cancelled yet. If every test record you created has since been closed, several tiles legitimately read 0. Before logging a defect, check whether any record actually matches that tile's definition right now.

Step 45: Reports Page Check

Open /dashboard/reports (separate from the Dashboard, reachable from its own sidebar link).

Expected:

  • Page opens without runtime error.
  • Summary cards for pending review, pending acknowledgement, and overdue action points are visible.
  • Status, priority, and meeting-status breakdown donut charts render, matching the counts you'd expect from the records you've created.
  • A monthly intake trend chart renders for the last six months.
  • The export button produces a CSV/print-ready summary combining SLA, workload, and trend rows.
Reporting should not be marked failed just because the database is too small for meaningful trend analysis. Mark it as revisit with larger data volume if the UI works but the sample size is too small.

15. Final Exit Criteria

Area Pass condition Result
Foundation Organization, departments, members, and roles are correctly rebuilt after reset. Pass / Fail
Auth flows Email verification, password reset, and the mandatory MFA challenge for admin roles all work and actually gate access (not just redirect once). Pass / Fail
Role security Wrong-destination access is blocked consistently, the access module reflects real permissions, and the forbidden page handles unauthorized attempts cleanly. Pass / Fail
Correspondence Full lifecycle from register to close works, including internal/external source, reopen, and second cycle. Pass / Fail
Documents Category CRUD, standalone and linked document flows, source type, archive, and permissions all work. Pass / Fail
Meetings Meeting creation, action point assignment, status update, held/close lifecycle, print view, and correspondence linking all work. Pass / Fail
Notifications Right event reaches the right user at the right stage without unread drift. Pass / Fail
Search Search loads correctly, returns permission-aware results, and opens the right destinations. Pass / Fail

Reports Reports page opens, charts render, and export works; small sample size alone does not count as a failure. Pass / Fail / Revisit

Recommended use: keep this file open while testing, fill the Pass/Fail cells directly in Word or PDF after printing, and log every failure immediately instead of trying to remember it later.
